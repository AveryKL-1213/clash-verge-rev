# 本地构建：网关维护、替换与回退

本文针对一台同时给局域网提供透明代理与 DNS 的 Mac。构建产物检查结束后，应在**替换 `/Applications/Clash Verge.app` 之前停止自动操作**，由使用者选择维护窗口并执行下面的切换。编译成功、代码测试通过、签名校验通过，都不等于已经验证这台 Mac 上的 TUN 网关流量。

## 现有拓扑与边界

- Mac：`192.168.50.2`；上游路由器：`192.168.50.1`。实施时仍需核对实际地址与网卡。
- 客户端把网关和 DNS 指向 Mac，通常不设置 HTTP/SOCKS 端口。
- Mac 的**物理上游网关仍应是路由器**，不能回指 Mac 自己。路由器向客户端通过 DHCP 下发 Mac 地址，与把路由器自己的上游默认路由指向 Mac，是两件事；后者可能形成 `.1 → .2 → .1` 环路。
- 保留所需的 `allow-lan`，但局域网代理端口、DNS 监听、控制 API 的访问范围应分别检查。HTTP/SOCKS 认证不等于透明 TUN 网关的客户端认证。
- 路由器已关闭 IPv6；其他 VPN、额外网卡和客户端自行启用的隧道仍应单独检查。
- 本文和配套脚本不停止应用、不安装或卸载服务、不修改路由、DNS、系统代理、转发参数或 PF。

## 为什么采用同一个生产应用标识

正常替换使用现有生产标识 `io.github.clash-verge-rev.clash-verge-rev`。配置位于：

```text
~/Library/Application Support/io.github.clash-verge-rev.clash-verge-rev
```

同标识的本地 release 会读取这份配置，可能进行版本迁移，通常不需要“先打开新应用导入，再卸载旧应用”。不要为了预先导入配置，同时启动两个生产实例。替换应用包也不意味着要删除配置目录。

如果以后改用完全独立的应用标识，还需要同步处理配置路径、服务通道／launchd 标识、IPC 路径和开机启动记录。仅改 `.app` 文件名不能隔离。即使 profile 和服务标识不同，DNS 的 53 端口、代理端口、系统 DNS、路由及 TUN 仍属于整台机器。

本地自用可以使用 ad-hoc 签名，无需购买 Developer ID 证书或提供 Apple 账号；这仍然属于签名，不能表述为“完全没有签名”。服务安装仍需要 macOS 管理员授权。界面和全部附带二进制都应来自约定的源码构建，不能仅重新编译界面却保留下载的 helper/core。

## 先做可用的恢复备份

只读摘要不会输出订阅或代理密码：

```sh
python3 scripts/local/gateway_snapshot.py inspect
```

完整备份必须明确指定一个**尚不存在、仓库之外**的目录，父目录需已存在。例如在自己的加密磁盘上建立私密备份目录后运行：

```sh
python3 scripts/local/gateway_snapshot.py backup \
  --output "$HOME/ClashVergeBackups/before-local-release-20261112"
```

脚本以目录 `0700`、文件 `0600` 保存：

| 文件 | 用途 |
| --- | --- |
| `installed-app.zip` | 完整旧应用包，保留资源与附带程序 |
| `application-config.zip` | 完整旧配置，包括订阅、覆写、规则和应用设置 |
| `network-state.json` | 接口、路由、转发参数、系统 DNS／代理、各网络服务设置、launchd 和 PF 状态 |
| `system-config/` 与索引 | 可读取的 PF 配置／anchor 文件和本应用的 launchd 配置 |
| `manifest.json` | 应用版本、来源路径、压缩包 SHA-256、采集失败项及完成状态 |

备份含订阅令牌、代理密码和网络信息，**没有加密**；私密权限不能替代加密。保存在受保护的本机或加密外置磁盘，不上传到 Git、聊天或公开云盘。临时目录不能作为唯一回退副本。脚本拒绝把备份写进 Git worktree。

普通用户通常无法读取 PF 的运行规则，脚本会记录失败而不自行请求提权。需要完整 PF 运行状态时，可由使用者先在终端执行 `sudo -v`，随后对同一命令添加 `--sudo-pf`，并选择另一个新的输出目录；该选项只给只读的 `pfctl -s` 查询使用 `sudo -n`，不会装载、清空或启停 PF。不要把整个脚本用 `sudo` 运行。

2026-11-12 的初始备份中，`pf_status`、`pf_rules`、`pf_nat`、`pf_anchors`、`pf_anchor_rules`、`pf_anchor_nat` 六项诊断均未能读取。正式维护前应按上一段补采，并查看失败是否已消除；在此之前，不能声称已经掌握当前运行的 PF 规则。不要通过关闭整个 PF 来绕过这项检查。

检查 `manifest.json` 的 `complete`、失败项和两个压缩包是否可以解压。`complete: true` 只说明备份流程结束，不代表所有权限受限的诊断都成功。运行中的应用会继续改写配置，所以这是实时备份，不是事务快照；正式停用旧应用后，再做一份配置一致的完整备份，并保留此前仍在运行时的网络状态快照。

另保留已知可用的旧版本安装文件。本次已核验的 `2.4.1` 应用备份包含三个旧组件：`Contents/Resources/resources/clash-verge-service`、`install-service`、`uninstall-service`。它们与当前旧 App 中的文件哈希一致，三个文件的严格代码签名检查均通过；当前安装的旧 helper 与其中的 `clash-verge-service` 哈希也一致。旧版安装器的名称与新版 `clash-verge-service-install` 不同，不能据此误判备份缺少安装器。

这些检查证明备份具备离线重装材料，**没有执行服务降级或恢复演练**，不能据此声称回退后的 TUN 已经可用。只有旧 `.app` 备份而没有核验匹配的安装器、服务和配置，不能视为完整回退方案。

## 维护前先准备独立的联网通道

在另一台客户端上准备手动恢复到：

1. 网关：`192.168.50.1`。
2. DNS：一个当前网络上可达、**不会再转发回 Mac** 的上游解析器；只有确认路由器 DNS 不回指 Mac 时，才能使用 `192.168.50.1`。
3. 如曾给客户端设置显式 HTTP/SOCKS 代理，暂时取消该项；断开重连并清理旧 DNS 缓存，避免继续使用 fake-IP 缓存。

先用一台设备验证这条路径确实能打开路由器管理页和普通互联网网站。这样即使 Mac 或 TUN 完全不可用，也能继续查资料和恢复。旁路会改为普通上游出口，原来必须通过代理访问的站点可能不可用；它不保证保持代理出口 IP。

如果路由器 DHCP 正在给全网下发 Mac 网关/DNS，可先只手动旁路维护设备；不要在未知状态下一次性改动全网。维护期间使用 Mac 的稳定物理上联网卡，避免同时切换 Wi-Fi、网线和其他 VPN。

## 正式切换的顺序

1. **构建与离线检查完成，但暂不启动产物。** 确认界面、Mihomo、服务和安装／卸载工具的来源、版本、架构、哈希及 ad-hoc 签名。确认本地修改不会被官方自动更新覆盖。
2. **准备上述两份备份和独立联网设备。** 记录当前开机启动、TUN、服务模式、系统代理及休眠设置，不把这一步等同于已完成流量验收。
3. **进入维护窗口，正常停止旧 TUN／退出旧应用。** 如有自动启动或自动重启机制，先通过对应应用设置防止旧实例立即回来。停止后核对本应用的旧 core，不用宽泛的 `killall` 终止其他代理或 VPN。
4. **由使用者替换 `/Applications/Clash Verge.app`。** 保留备份；不要用清理工具顺带删除配置。不要把生产版本从临时目录或构建目录直接长期运行。
5. **打开新应用，按其服务管理界面安装／更新配套服务。** 同一 production service 标识下，目标服务安装器能够停止既有 launchd 服务并替换文件，因此不需要把“先手工卸载旧服务”作为固定前置步骤。应用包替换本身不会保证旧 helper 已更新，必须核对实际运行的服务及 core。
6. **确认配置后再开启 TUN。** 保留需要的 LAN 能力，检查 DNS 53 监听、控制 API 监听和访问限制、TUN 协议栈、fake-IP／规则、Mac 物理上游路由。不要同时运行旧版、新版或开发版 TUN。
7. **先验收一台客户端，再恢复其他客户端。** 依照下面的表格检查，最后再恢复需要的开机启动，并在合适时机验证重启及长时间运行。

仅在服务安装失败、服务标识发生变化或确有旧版本残留时，才使用匹配版本提供的服务卸载流程，然后安装目标版本服务。避免凭猜测删除 `/Library` 文件、删 launchd plist 或停用名字相似的其他后台项。

后台条目名称可能来自应用关联信息、服务可执行文件名及签名信息；源码中的显示名／标识可控制一部分，但 macOS 的归属判断和缓存会影响最终显示。不能保证只改一个字段就会立即出现指定名称。用真实路径、launchd label、版本和签名核对身份，比只看“允许在后台运行”页面的人名可靠。

## 最保底的回退

如果新版界面打不开，可在确认客户端已旁路、生产 core 已停止后，直接调用新版随包卸载器（不要在正常运行时执行）：

```sh
sudo "/Applications/Clash Verge.app/Contents/Resources/resources/clash-verge-service-uninstall" --debug
```

回退应恢复**旧应用 + 匹配的旧服务／core + 升级前配置**，不能只把旧 `.app` 拖回来而继续使用新服务或已经迁移的配置。

以下顺序针对**已经安装新版 `2.7.7` 服务，需要回到旧 App `2.4.1`** 的情况。仅完成本地构建、尚未替换应用和服务时，不需要执行卸载。

1. **先让维护客户端旁路联网。** 使用上面的路由器网关和独立 DNS，不依赖正在恢复的 Mac。
2. **停止新版 TUN/core，保留新版 App 直到卸载完成。** 将新配置和失败诊断保存到另一个私密目录，避免覆盖唯一旧备份。使用新版服务管理界面的卸载流程，随后退出新 GUI。若 GUI 无法操作，先退出它，再执行仍位于 `/Applications` 的新版卸载器：

   ```sh
   sudo "/Applications/Clash Verge.app/Contents/Resources/resources/clash-verge-service-uninstall" --debug
   ```

   使用新版卸载器清理新服务及其批准的内核副本；不要先覆盖 App 导致丢失卸载器，也不要用旧 `uninstall-service` 代替新版卸载器。
3. **核验服务确实停止并注销。** 检查下面的查询，只有明确报告找不到该服务才算注销；权限错误不等于服务不存在。检查进程列表，确认本次应用的 service 和 core 已退出。若仍在运行，停在此处排查，不继续覆盖文件，也不使用宽泛的 `killall`。

   ```sh
   sudo launchctl print system/io.github.clash-verge-rev.clash-verge-rev.service
   pgrep -fl 'clash-verge-service|verge-mihomo'
   ```

4. **恢复旧 App 和完整升级前配置。** 在所有 Clash Verge 实例关闭时，先把备份解压到独立恢复目录核验，再恢复到原位置。不要合并两代配置；用户配置应由原用户拥有，不要整段用 `sudo` 解压到用户目录。
5. **安装旧包配套服务。** 启动已恢复的 `2.4.1`，使用 TUN 控制旁的 **Install Service／安装服务** 按钮；旧 GUI 会提权调用随包 `install-service`。若 GUI 无法完成，退出旧 GUI 后可执行以下离线安装命令：

   ```sh
   sudo "/Applications/Clash Verge.app/Contents/Resources/resources/install-service" --debug
   ```

   该安装器从自身同目录读取旧 `clash-verge-service`，重新创建 helper 和 launchd 配置，并执行 `enable`、`bootout`、`bootstrap`、`start`。因此，新版卸载阶段留下的禁用标记由旧安装器重新启用，无需手工复制 root helper。
6. **核验实际安装和运行状态，不能只看退出码。** 旧 App `2.4.1` 要求服务版本 `1.1.1`。旧安装器会忽略部分 `launchctl` 子命令错误，所以退出码 `0` 不代表服务已经运行；新版卸载器的部分停止命令也采取尽力而为的方式。检查 launchd 中的路径、`state = running` 和 PID，并核验安装后的 helper 哈希：

   ```sh
   sudo launchctl print system/io.github.clash-verge-rev.clash-verge-rev.service
   shasum -a 256 "/Library/PrivilegedHelperTools/io.github.clash-verge-rev.clash-verge-rev.service.bundle/Contents/MacOS/clash-verge-service"
   ```

   本次已核验旧 helper 的 SHA-256 为 `1597f6adab59297d34acecfe29fcb77af1e0b693ff367b557a9923511a645dfa`。这是这份已保存备份的预期值，不应用来判断其他旧版本。旧 GUI 还应能连接服务并启动其配套 core；确认后才恢复旧版 TUN。
7. **按快照恢复必要网络设置并验收。** 逐项比较物理路由、当前网络服务的 DNS／代理、转发参数和相关 PF anchor。只有确知被本次切换改变的设置才恢复。网络服务原本使用 DHCP／自动 DNS 时恢复该方式，原本有手动地址时恢复原值。先验证一台客户端的 DNS、透明 TCP／UDP 和局域网访问，再恢复全网使用。

旧版安装调用可查 [Clash Verge `v2.4.1` 的服务代码](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.4.1/src-tauri/src/core/service.rs)，旧安装器逻辑可查 [service `1.1.1` 对应源码](https://github.com/clash-verge-rev/clash-verge-service/blob/e9a9bbc144715992c2d65a9752140a7a06562506/src/install.rs)。上述顺序经过源码和离线备份核验，**实际降级安装、断网恢复和 TUN 流量验收仍未执行**。

不要把备份的运行路由表或 launchd 状态全文“回放”为命令，也不要把整个旧系统配置目录覆盖回去。不要执行 `pfctl -F all`、清空全部路由、关闭整个 PF，或把全部网络服务 DNS／代理一刀切；这些可能破坏其他 VPN、防火墙、Internet Sharing 或其他网络服务。PF 文件备份与当时运行规则也可能不同，应先比较。

TUN 退出后如果 IP 转发仍开启，客户端流量可能经普通路由直接出去。`allow-lan` 的来源限制和 macOS 上的 TUN 路由选项不能单独证明“断代理即断网”。如要求严格防止直连，需另外设计、审查并实测有明确上游例外的 PF 规则；本文不自动添加这类规则。

## 频繁开发时保持网关稳定

| 工作 | 方式与边界 |
| --- | --- |
| 纯前端修改 | 优先 `pnpm web:dev` 配合现有 mock／浏览器调试；浏览器不具备完整 Tauri 能力。不要把页面接到生产控制 API 做写操作 |
| 编译、单元测试、静态检查 | 可以在独立 worktree 进行，不需要启动生产 release，也不需要安装 service |
| Rust／Tauri 本机联调 | 使用项目的开发 profile 和开发服务通道；先确认实际配置目录和服务标识为开发用途，不导入真实订阅到 Git 目录 |
| TUN、DNS、服务安装的端到端调试 | 优先用独立测试机／测试网络。必须使用本机时，进入维护窗口、旁路客户端、停生产 TUN 后再开始 |
| 新 release | 重复完整备份、替换、配套服务检查和客户端验收；不要在后台自动替换网关运行版本 |

开发 profile 只隔离应用数据，不代表系统网络隔离。即使开发版使用独立服务，也不能与生产版同时占用 53／代理端口、接管系统代理或创建相互冲突的 TUN 路由。开发结束后退出开发实例，检查相关服务与网络状态，再恢复生产实例。

## 验收记录模板

以下都需要在实际切换后填写；未执行的项目必须记为“未验证”。

替换应用并按界面安装／更新服务、开启核心后，以当前普通用户运行只读检查。将参数替换为这次最终产物的 `provenance.json`：

```sh
python3 scripts/local/verify_install.py /绝对路径/最终产物/provenance.json
```

脚本检查应用内六个可执行文件的 SHA-256、已安装 root helper 与应用内 service 的一致性、launchd 状态，以及本用户 core IPC socket 的路径／所有者／权限。它不会执行 helper（包括 `--version`）、安装或停止服务，也不读取真实配置或认证 secret，不请求控制 API。

退出码 `0` 表示这些检查通过；`2` 表示正常完成检查但存在未安装、文件不符、服务未运行、socket 未出现或权限不足等未验证项；`1` 表示输入的 provenance 不可读或不符合格式。旧版仍在运行时出现不符是预期结果，不代表检查脚本损坏。不要通过 `sudo` 强行消除“权限不足”提示，应先核对是否确实以正常用户完成安装与服务启动。

匹配的文件和 socket 权限不能证明当前 core 的版本、socket 活性或网关流量；下面的客户端验收仍须完成。离线检查其他应用包可加 `--app /路径/Clash\ Verge.app`，但 helper 和 IPC 检查仍针对这台 Mac 上安装的生产服务。

| 检查项 | 通过条件 | 结果 |
| --- | --- | --- |
| 应用／服务／core | 实际运行路径、版本、架构、哈希符合本地发布清单；没有旧 core 并行 | 未验证 |
| Mac 上联网关 | 物理上游仍为路由器，没有回指 Mac 的默认路由／DNS 递归 | 未验证 |
| 客户端 DNS | DNS 指向 Mac 时解析正常；直连与代理域名均符合规则 | 未验证 |
| 透明 TCP／UDP | 客户端不配置显式代理也能按规则访问；常用视频／通话等 UDP 业务正常 | 未验证 |
| 局域网功能 | 路由器管理页、NAS、打印机等必要资源可达 | 未验证 |
| 暴露面 | 管理 API 和代理／DNS 仅向预期来源开放；从不受信任网段实际验证拒绝 | 未验证 |
| 故障与旁路 | 事先选定允许的出口行为；维护客户端可独立恢复普通联网 | 未验证 |
